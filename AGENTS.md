## 1. Overview & Core Constraints

### 1.1 Role & Scope
- You are a coding assistant for the **speak5220** project.
- The repository has two parts:
  - **`app/`**: the Speak5220 application, a Qt/C++ tool for creating LPC
    speech data and building PHROMs. This is where development happens.
  - **`investigation/`**: the research record (hardware, firmware, capture
    tools and the C emulator). The emulator, and the Python encoder that
    the application's encoder re-implements (in git history, last changed
    in commit `6abe9ed`), are retired reference implementations. **Do not modify `investigation/`** unless the user explicitly
    asks.
- Follow these instructions **in addition to** any `AGENTS.md` files in the
  task directory or above.
- For pull-request workflows, see the template in `.github/PULL_REQUEST_TEMPLATE/`; issues use the templates in `.github/ISSUE_TEMPLATE/`.

### 1.2 Git Operations
- **Do not** run `git add`, `git commit`, `git push`, `git stash`, or any command that modifies repository state unless the user explicitly requests it.
- Read-only commands (`git status`, `git log`, `git diff`, `git show`) are permitted.
- When asked to commit, the pre-commit hooks must pass. **Never** use `--no-verify`.

### 1.3 Naming
- Never use planning-phase terminology (e.g., `phase0`, `mvp-phase`) in code, files or identifiers under `app/`.
  - The `investigation/captures/phaseN/` directories are names from the historical capture campaigns and are exempt.
- Use **descriptive, domain-oriented names**: `frame_codec`, `lattice_filter`, `pitch_tracker`, `phrom_allocator`, `speak_external_stream`.

### 1.4 Content Restrictions
- Do **not** include advertisements, promotions, or commercial references.
- Omit "generated by", "co-authored by", or tool/service attributions.

## 3. Testing & Quality Assurance

### 3.1 Unit Testing
- Source of truth: `TESTING.md`.
- Unit tests are the **primary** methodology; prefer them for all new or modified behaviour.
- Framework: Google Test with Google Mock.
- Requirements:
  - Mock dependencies; tests must be **deterministic**.
  - No file system, audio device, thread pool, system clock, network, or external service dependencies.
  - Keep tests isolated and fast.
  - Use interface-based dependency inversion and constructor injection.
  - Name tests by behaviour, in `PascalCase` (Google Test forbids underscores in test names): `TEST(PhromAllocatorTest, StartsNewPhromWhenNextPhraseDoesNotFit)`.
- Classification:
  - Classification follows the **directory**: sources under `app/tests/unit/` (and `app/tests/gui/unit/`) are labelled `unit`, those under `app/tests/functional/` (and `app/tests/gui/functional/`) are labelled `functional`. There is no list to update.
  - Use `functional` **only** when the objective cannot be met with a unit test.
  - Tests touching the file system, real audio, the reference data in `app/golden/`, or full pipelines **must** be `functional`.
  - A file whose tests would span both categories must be **split into two files**, one per tree.
- Fixtures: fixture projects live in `app/projects/` (stored unpacked), never in `app/tests/`. Mechanically derived data (such as the WAV copies of the corpus) is generated, not committed.
- Reference data in `app/golden/` is a fixed regression baseline:
  - **Never** change the emulator's reference data, unless the reference datasheet changes.
  - Regenerate the encoder's reference data only for an intended improvement, in its own commit that records the quality before and after; the quality data in `app/golden/quality/` is regenerated with it.
  - Ask the user before changing any reference data (§12).
- Output: tests and scripts must write through a caller-chosen output directory (the CLI's `--output`, or a `QTemporaryDir` in tests), never into `app/projects/`, `app/golden/` or `app/tests/`. The exceptions are the scripts in `app/scripts/golden/` (`generate_golden.py`, `encoder.py`, `measures.py`, `basic_programs.py`), run by hand to create the reference data, and `app/scripts/output-hashes.sh --record`, which records the export baseline in `app/golden/output-hashes/` (TESTING.md).
- By-hand checks (the full-corpus check, the benchmark, the window check) are functional tests with the `DISABLED_` prefix, run only by their scripts (`corpus-check.sh`, `benchmark.sh`, `window-check.sh`) with `--gtest_also_run_disabled_tests`; CTest never runs them.
- CI: the default unit-test lane must stay fast and mocked; do **not** add functional tests to it.

### 3.2 Logging
- Logging uses spdlog, at three selectable levels, to the console, a file (`--log-file`), or both. Warnings and errors are always logged.
- **info**: normal lifecycle messages, stage transitions, validation summaries.
- **debug**: configuration details, branch decisions, resolved paths, chosen encoder options.
- **trace**: per-frame, per-sample and per-slot state, tight loops, intermediate values (pitch candidates, lattice sums, FIFO contents).
- Guidelines:
  - Use the least verbose level that still explains the behaviour.
  - Keep text concise and action-oriented for both console and file output.

## 4. C++ Coding Standards

### 4.1 Baseline & Tooling
- Follow the [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html), with these agreed exceptions, each recorded in the configuration with a comment:
  - `.cpp` source files (the guide prefers `.cc`).
  - Qt API names: overrides and Qt-mandated members keep Qt's names (`paintEvent()`, `rowCount()`, `data()`, `Q_PROPERTY` accessors). Signals and slots the application defines itself follow the guide.
  - Qt macros and ownership: `Q_OBJECT`, `signals:`/`slots:` and parent-owned `new QWidget(parent)` are allowed; everything else uses `std::unique_ptr` or values.
- C++20, no compiler extensions, no exceptions: errors are returned as `Status`/`StatusOr<T>`.
- **Never** use manual column-alignment (e.g. double-spacing before `=`, aligning continuation lines to opening parentheses) — clang-format will undo these and leave violations.
- Use static analysers (`clang-tidy`, `cpplint`) and sanitizers where available in the Nix environment. The pre-commit hooks run them; fix failures rather than suppressing them. An exception to the style guide goes in the configuration, with a comment saying why.

### 4.2 Source File Headers
- Every C++ source and header **must** start with an SPDX header **above** all other content.
- Template:
  ```cpp
  /*
   * File:        frame_codec.cpp
   * Module:      lpc
   * Purpose:     Packs and parses TMS5220 frames in the chip's bit order
   *
   * SPDX-License-Identifier: GPL-3.0-or-later
   * SPDX-FileCopyrightText: (c) 2026 Simon Inns
   */
  ```
- `File` must match the filename **exactly** (case-sensitive).
- `Module` must describe the logical component (the `s5core` subdirectory, or the GUI area).
- `Purpose` must be a concise, domain-oriented description.
- Other source files (CMake, Nix, shell, Python, workflow YAML, Qt `.ui`/`.qrc`) carry the two SPDX lines in their own comment syntax.
- Documentation (Markdown) carries **no** header.

### 4.3 Custom Additions

#### 4.3.1 Interface Design
- Prefix abstract interface names with `I` (e.g., `IVsmBus`, `IQualityMetric`).
- Methods: `virtual` with `= 0` for pure virtual.
- Always include a virtual destructor: `virtual ~IInterfaceName() = default;`

#### 4.3.2 Memory Safety
- Prefer RAII: use smart pointers (`std::unique_ptr`, `std::shared_ptr`) for ownership.
- Qt widgets owned by a parent are the exception: `new QWidget(parent)` is allowed.
- Use assertions for pointers that must **never** be null.
- Range-check container access; prefer `std::span` or bounds-checked methods over raw arrays.
- Document ownership semantics explicitly.

#### 4.3.3 Concurrency
- Document thread-safety guarantees for every public class or function.
- Use `std::mutex`, `std::atomic`, or message-passing; never rely on undefined behaviour.
- Mark shared vs thread-local state explicitly; prefer immutable data where possible.
- Qt objects are used only on the thread that owns them. Background jobs (encoding, Optimise, synthesis) return results to the GUI through queued signals.
- Parallel work must give the same result whatever the thread count (TESTING.md, Determinism requirements).

#### 4.3.4 File Organisation
- Close namespaces with a trailing comment: `}  // namespace speak5220::core`

#### 4.3.5 Constants & Clarity
- Avoid magic numbers; define named constants with descriptive comments.
- Coding tables (energy, pitch, K, chirp) are `constexpr` and cite their datasheet table.
- Reference authoritative specs when implementing standards (see §9.4).

#### 4.3.6 Specification References
- Format: `// <Source> <Section>: <description>`
- Examples:
  - `// speak5220 datasheet §8.8: Booth multiplier with 14-bit wrap.`
  - `// speak5220 datasheet §12.9: a Speak External stream needs at least 9 bytes.`
  - `// TI TMS5220 data manual, Table 3: coding table for K1.`
  - `// Acorn Speech System User Guide Section 6: OSBYTE &9F writes to the speech processor.`
  - `// Jensen and Taal 2016, Eq. (2): the normalised segment correlation.`
- Supported sources: the speak5220 reference datasheet, TI data manuals (TMS5220, TMS6100), US patent 4,335,277, Acorn manuals (Speech System User Guide, DFS, BBC Micro User Guide), IEC.
- Code re-implemented from the retired references names its original (e.g. `// Re-implements tms5220enc.py trackPitch().`), so the two can be compared; the Python encoder's files are in git history at commit `6abe9ed`.

#### 4.3.7 Commenting
- Use inline comments **above** function declarations for purpose, parameters, and return values when non-obvious.
- Explain the approach before complex algorithms.
- Document rationale behind non-obvious decisions.
- Use `// TODO: <description>`; avoid redundant comments.

## 5. Performance

- **Profile before optimising**; prefer measurable gains over premature micro-optimisation.
- Minimise copies: use references, move semantics, and `const` where possible.
- Document Big-O complexity for public algorithms; note cache-locality assumptions where relevant.
- Flag any change that increases memory use by >10 % or execution time by >5 % for design review. Measure with `app/scripts/benchmark.sh` (TESTING.md).
- The hot paths are the emulator's per-slot step, the encoder's closed-loop synthesis and the quality measures, all run many times by Optimise. Keep them free of allocation, and watch for virtual calls per sample or per slot in profiles.

## 6. Development Environment

- The project uses **Nix**; the provided development shell is authoritative.
- Run normal workflows inside the project shell:
  `nix develop --command <command>`
  - For application work, the smaller `nix develop .#app --command <command>` is enough (it is the shell CI uses).
  - Do **not** use `path:$PWD` (or any `path:` flake reference). It copies the whole working tree into the Nix store, including the tens of gigabytes of gitignored captures under `investigation/`. The default git flake reads only tracked files.
  - Because of that, `nix build`, `nix run` and `nix flake check` do not see untracked files. Commands run *inside* the shell (CMake, CTest, the scripts) work on the working tree as usual. Before running those three on new files, ask the user to stage them, because agents do not run `git add` (§1.2).
- Temporary tools (profiling, debugging, one-off analysis):
  - Use ad-hoc shells:
    `nix shell nixpkgs#<tool> --command <tool> <args>`
    `nix shell nixpkgs#<tool1> nixpkgs#<tool2> --command <command>`
- Do **not** modify `flake.nix` solely for temporary dependencies.
- Always provide the Nix-based equivalent alongside plain shell commands.

## 7. Pre-Session Nix Setup

- If space is critically low (< 20% free), warn the user before proceeding.
- Create a temporary profile:
  ```bash
  export AI_AGENT_PROFILE=\$(mktemp -d)/nix-profile
  export NIX_USER_PROFILE_DIR=\$AI_AGENT_PROFILE

After completing a development session or task, perform the following steps to clean up the Nix store in the temporary profile:

  ```

### 9.2 Published Site Structure (`docs/`)
- Navigation is listed explicitly under `nav:` in `mkdocs.yml`. **Every new
  page must be added there**, or it will not appear in the site navigation
  (and `mkdocs build --strict` warns about it).
- The application's documentation lives under `docs/application/`, as its own
  top-level navigation section:
  - `getting-started.md` — installation and a quick-start walkthrough.
  - `user-manual/` — one page per area (phrases and import, waveforms and
    playback, the encoder and Optimise, PHROMs, export, BBC Micro disc, the
    CLI); explains *what a feature does and how to use it*.
  - `reference/` — the exact meaning, type, default and valid range of every
    project-file YAML key, encoder option and CLI option, and the byte layout
    of every export format.
- Page conventions:
  - Start with a single `#` H1 title matching the navigation entry.
  - Link between pages with relative `.md` paths (e.g.
    `../reference/project-file.md`), never site URLs.
  - Use tables for key/option reference material, and `!!! note` / `!!! warning`
    admonitions for caveats.
  - Cite the governing source inline where behaviour is spec-driven
    (e.g. `datasheet §12.8`), matching the format in §4.3.6.
- New user-facing feature ⇒ a `user-manual/` page (or section) **and** the
  corresponding `reference/` entries for any new keys or options.
- Verify the site still builds before finishing:
  `nix develop --command mkdocs build --strict`.
  Preview with `nix develop --command mkdocs serve`.

### 9.3 Keeping Documentation Current

When a change touches any of the following, update the listed documents in the

| Change | Update |

| Changed testing rules or layout | `TESTING.md` and §3 of this file |

Additional rules:
- Documentation must describe **implemented** behaviour. Where something is
  designed but not yet implemented, say so explicitly on the page rather than
  documenting it as available.
- Do not include change history, release notes, or "recently added" wording in
  documentation — that belongs in git.
- Update existing pages in place rather than adding parallel pages that
  duplicate them; remove documentation for removed features in the same task.
- If you detect a code/documentation mismatch, follow §9.5: warn the user and
  offer to resolve it. **Never** silently leave a mismatch.

### 9.4 Authoritative Sources
- **The TMS5220 and its data** (frame format, coding tables, timing, lattice
  arithmetic, VSM images, Speak External):
  - Start: `docs/technical/datasheet/index.md`
  - Authoring speech data (PHROM and TI layouts, Speak External): `docs/technical/datasheet/authoring.md`
  - Open questions the datasheet does not settle: `docs/technical/datasheet/gaps.md`
- **TI's original documents**: `docs/technical/sources/` (the TMS5220 and
  TMS6100 data manuals, US patent 4,335,277). Use them where the reference
  datasheet says the original still applies.
- **BBC Micro speech**: the [Acorn Speech System User Guide](https://chrisacorns.computinghistory.org.uk/docs/Acorn/Manuals/Acorn_SpeechSystemUG.pdf) (Sections 5–7).
- **Speech quality**: the quality measures and their sources: libfvad (WebRTC VAD), SPTK 4 (LPC analysis, REAPER, WORLD's Harvest), and pystoi with Jensen and Taal, "An Algorithm for Predicting the Intelligibility of Speech Masked by Modulated Noise Maskers" (2016) for ESTOI.
- **Rule**: if code conflicts with assumptions, align code **and** tests to the
  reference datasheet first. The datasheet itself is changed only when the user
  asks.

### 9.5 Documentation Consistency
- The documents of §9.1 and the code's comments must stay aligned with implemented behaviour.
- When changing code that affects documented behaviour, **update the documentation in the same task** whenever practical.
- If you detect a code/documentation mismatch:
  - Explicitly warn the user.
  - Offer to update the documentation to match the code (or the code to match the documentation).
- **Never** silently leave mismatches unresolved.
